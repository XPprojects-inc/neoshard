# Поведенческая спека: realtime Gateway

Источник: публичная документация Discord Gateway. Ниже — **поведение**, которое
стоит воспроизвести; формат, имена и кодирование у NeoShard свои (см. `spec/proto`).

## Жизненный цикл сессии (наблюдаемое поведение оригинала)

1. Клиент открывает WebSocket (параметры: версия, кодирование, сжатие).
2. Сервер первым шлёт `Hello { heartbeat_interval }` (~41.25 с).
3. Клиент ждёт `interval * jitter` (jitter ∈ [0,1)), затем шлёт heartbeat
   каждые `interval`. Каждый heartbeat несёт последний полученный `seq`.
4. Сервер отвечает `HeartbeatAck`. Если ack не пришёл до следующего heartbeat —
   соединение «зомби»: клиент закрывает его кодом не-1000 и делает resume.
5. Клиент шлёт `Identify { token, properties, intents, shard? }`.
6. Сервер отвечает `Ready { session_id, resume_url, user, guilds(unavailable stubs) }`,
   затем по событию `GuildCreate` на каждую гильдию (lazy).
7. Все dispatch-события несут монотонный `seq` в рамках сессии.

## Resume

- Клиент переподключается к `resume_url` и шлёт `Resume { token, session_id, seq }`.
- Сервер воспроизводит пропущенные события после `seq` и шлёт `Resumed`.
- Если сессия протухла или буфер переполнен — `InvalidSession { resumable: bool }`;
  клиент ждёт 1–5 с случайно и делает новый Identify.
- Сервер может попросить переподключиться (`Reconnect`) — например, при деплое узла.

## Закрывающие коды (смысловые классы)

| класс | resume? | пример |
|---|---|---|
| неизвестная ошибка / decode error | да | 4000, 4002 |
| не авторизован / ошибка токена | нет | 4004 |
| превышен лимит отправки | да | 4008 |
| сессия истекла | нет, re-identify | 4009 |
| неверная версия API / intents | нет | 4012–4014 |

## Rate limits Gateway

- 120 исходящих сообщений от клиента за 60 с на соединение.
- Identify ограничен (у оригинала — 1 за 5 с на shard-бакет, суточная квота).

## Intents

Битовая маска подписок, сервер не шлёт события вне маски (экономия трафика).
Привилегированные intents (члены гильдии, presence, контент сообщений) — для ботов.

## Lazy guilds / member list

Большие гильдии не присылают полный список участников; клиент запрашивает
«окно» списка участников для видимого диапазона (виртуализация на сервере).

## Решения NeoShard (отличия)

| что | у NeoShard |
|---|---|
| кодирование | Protobuf (`prost`) всегда, бинарные фреймы |
| сжатие | zstd per-message, словарь опционально; негоциируется в query `?compress=zstd` |
| heartbeat | 30 с по умолчанию, тот же jitter; ack обязателен |
| resume | буфер последних 1024 событий/сессия в памяти узла + TTL 120 с; в кластере — через NATS JetStream (TODO) |
| батчинг | сервер склеивает dispatch-события в `DispatchBatch` (до 16 мс окна) — меньше фреймов и меньше пересечений JS↔WASM |
| URL | клиент знает только базовый URL инстанса; `GET /.well-known/neoshard` отдаёт gateway/api/media эндпоинты |

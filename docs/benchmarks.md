# Бенчмарки

Машина: Windows 11, 12 логических ядер, клиент нагрузки и сервер на одной ОС,
PostgreSQL 18 локально. Сервер — release, `--release` профиль, mimalloc.

## Gateway: соединения (`server/loadtest`)

```bash
neoshard-loadtest seed --sessions 100000          # 5000 пользователей × 20 сессий, одна гильдия
neoshard-loadtest connect --sessions 15000 --source-ips 127.0.0.41,…,127.0.0.44 --rate 400 --messages 3
```

| прогон | готово | отказы | память сервера | fan-out (1 сообщение → все сессии) |
|---|---|---|---|---|
| 10 000, до оптимизаций | 10 000 | 0 | 3 256 МБ (≈ 325 КБ/соед.) | средн. 261 мс, макс. 487 мс |
| 10 000, буферы 4 КБ + без zstd на мелких кадрах | 9 614 | 386 | 2 423 МБ | средн. 140 мс |
| 2 000, + сжатый буфер реплея, эфемерные события | 2 000 | 0 | +48 МБ (≈ 24 КБ/соед.) | — |
| **15 000, + presence не рассылается в больших гильдиях** | **14 999** | **1** | **234 МБ (≈ 14.6 КБ/соед.)** | **средн. 231 мс, макс. 471 мс, доставлено 100%** |
| 100 000 (до исправления presence) | ~16 000 | упор в ОС | — | — |

**Что нашли и исправили по ходу замеров:**
1. Буферы tungstenite по умолчанию 128 КБ на чтение/запись → 4 КБ.
2. zstd на каждом крошечном кадре для каждой сессии → кадры < 512 байт не сжимаются.
3. Реплей-буфер держал развёрнутые `v1::Event` (~400 Б) и сотни presence-событий
   соседей → хранятся закодированные байты, presence/typing — эфемерные (`seq = 0`).
4. Presence каждого входа рассылался всей гильдии — O(N²) в гильдии на 100k сессий →
   в гильдиях > 250 участников presence только через ленивый список участников.
5. Состояние handshake (sqlx-запросы, Ready) жило в future соединения всё время → `Box::pin`.

**100 000 на одном узле — не подтверждено на этой машине.** Клиент и сервер на
одной Windows держат по 2 сокета на соединение; на ~30k ОС отвечает WSAENOBUFS
(10055). По линейной экстраполяции 15k-замера 100k соединений ≈ 1.5 ГБ памяти;
узкое место — Identify (~390/с: ~12 запросов к БД на вход) и fan-out одного
события на все сессии одним потоком роутера (≈ 15 мкс/сессия → ~1.5 с на 100k).

Методика для настоящего замера (Linux-сервер, 2–4 машины-генератора):
```bash
# сервер
ulimit -n 1048576; sysctl -w net.core.somaxconn=65535 net.ipv4.tcp_max_syn_backlog=65535
NEOSHARD_DB_MAX_CONNECTIONS=128 neoshard-server
# каждый генератор (25k соединений, свои source IP)
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
neoshard-loadtest connect --url ws://SERVER:8080/gateway?v=1 --api http://SERVER:8080 --sessions 25000 --rate 400
```
Следующие оптимизации: шардирование роутера по ядрам, кэш снапшота Ready на гильдию,
общий закодированный кадр для сессий с одинаковым фильтром.

## Граница JS↔WASM и протокол (`cargo bench -p neoshard-core --bench boundary`)

| операция | время |
|---|---|
| encode `UpdateBatch` из 64 сообщений | 5.6 мкс |
| decode `UpdateBatch` из 64 сообщений | 22.1 мкс |
| decode 64 отдельных `Update` | 23.8 мкс |
| кадр Gateway с 64 событиями: encode + zstd + decode | 69.5 мкс |

Вывод для ADR-0009: (де)сериализация — единицы микросекунд на кадр; поэтому
дорогой остаётся только сам *переход* границы и аллокация на стороне JS —
пакетный `drain()` раз в кадр делает один переход вместо десятков.
